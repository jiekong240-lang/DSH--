## 技术范围（纪要里已经写明的草案）

底座与约束：

- 运行底座：**DeepSeek Harness**；主要推理端：**DeepSeek API**。
- **不修改官方 Harness 核心**。插件、Skills、MCP 等扩展是否可用，以当前安装版本和真实 Schema 为准；做不到的接口写「当前不支持」或「未核实」。
- Harness 负责运行与工具协调；执行、测试、验收要单独建设。增加模块不能当成模型本体推理能力已经提高。

边写边测（纪要采用的主流程，不是「写完再测一次」）：

理解需求 → 审计环境 → 理解仓库 → 定位相关代码 → 设定工作单元 → 修改 → 检查差异 → 跑相应测试 → 分析真实失败 → 最小修复 → 回归 → 独立交付。

| 层 | 名称 | 主要检查 |

**完成态**：只有 **Verified**（独立验收通过）可以直接算成功。Planned、Executed、Produced、Failed、Unknown / Pending 都不算成功。模型声称完成、工具返回成功、测试退出码为 0、另一个模型表示认可，都不自动等于任务成功。零测试或错误测试配置要单独识别。

**顺序**：先证明单 Agent 能交付真实软件，再把多 Agent 当作研究变量。纪要里的四种拓扑（A 单 Agent、B 固定角色串行、C 共享工作区并行、D 隔离工作区并行）以及后来的能力分组 A–F，都是拟议对照，不是已跑完的实验。共享桌面上的键鼠单写入租约同样标为待实验设计。
